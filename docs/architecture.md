# BOQLint 架构

BOQLint `v0.1.0` 是纯静态、浏览器本地运行的 React 应用。部署端只提供 HTML、JavaScript、CSS 和虚构示例文件；用户选择的工作簿不会发送到部署端或第三方服务。

## 设计目标

- `.xlsx` 解析、字段映射、检查和报告导出全部在浏览器完成。
- 规则逻辑与 React 视图分离，便于单元测试和复用。
- 不修改输入工作簿；所有导出都是新对象和新文件。
- 模板识别可解释、可人工覆盖，避免依赖固定表头行。
- 对 10,000 条明细保持合理响应，长循环分批执行并报告阶段进度。
- 正常 Pages 构建与单文件离线构建共享同一业务代码。

## 数据流

```mermaid
flowchart LR
  A["本地 .xlsx / 内置虚构示例"] --> B["文件类型与大小校验"]
  B --> C["ExcelJS 解析为工作簿快照"]
  C --> D["工作表选择与表头候选评分"]
  D --> E["用户确认字段映射"]
  E --> F["行分类与标准化"]
  F --> G["规则引擎分批检查"]
  G --> H["筛选、分页、原始行上下文"]
  H --> I["本地生成 CSV / JSON / XLSX 报告"]

  J["localStorage: 语言 / 主题 / 规则配置"] --> D
  J --> G
```

没有从 `C` 到网络服务、数据库或遥测系统的路径。

## 层次划分

### 1. 表示层

React 负责四步状态机：导入、映射、检查、结果。组件展示进度、错误、预览、筛选、分页、上下文和导出操作，不承载金额计算或规则判断。

用户可见文本通过中英文资源集中管理。主题由 CSS 自定义属性实现；严重程度同时使用文字、图标和颜色。状态变化使用语义化 HTML、焦点管理和适当的 ARIA 属性。

### 2. 工作簿适配层

ExcelJS 只负责读取/生成 `.xlsx`。解析后，应用把每个工作表转换为可序列化快照，包括：

- 工作表名称、可见状态和有效范围；
- 单元格原始值、文本、公式、缓存结果和地址；
- 行/列隐藏状态；
- 合并单元格范围；以及
- 文件名、大小和工作表数量等基础元数据。

域层不持有 ExcelJS `Workbook` 实例。清除文件时，页面同时释放原始缓冲区、工作簿对象、快照、映射和结果引用。

### 3. 识别与映射层

表头检测扫描每张表前 30 行，对标准字段同义词进行归一化和加权评分。候选结果包含行号、匹配字段、置信度和建议映射，用户可选择其他表头行或逐字段修改列映射。

内部字段保持稳定：`serial_no`、`item_code`、`item_name`、`item_feature`、`unit`、`quantity`、`unit_price`、`total_price`、`remarks`。

### 4. 域与规则层

域层使用普通 TypeScript 数据结构和纯函数：

1. 标准化可比较文本和项目编码；
2. 严格解析数值和公式缓存状态；
3. 区分明细、章节、汇总、重复表头和空白行；
4. 按工作表建立重复/单位一致性索引；
5. 按固定顺序运行启用的规则；
6. 生成统一问题对象。

每个问题至少包含严重程度、规则编号、工作表、Excel 行号、字段/列、项目编码、原始值、问题说明和修复建议。`CALC-001` 使用 `decimal.js`，并记录表内合价、计算合价和差额。

规则定义包含稳定 `ruleId`、默认严重程度、说明、修复建议、是否为不可关闭核心规则和默认启用状态。规则配置先通过结构校验，再进入规则引擎。

### 5. 报告层

报告层只接收可序列化的运行快照，不接收原始工作簿对象。

- CSV：UTF-8 BOM，一行一个问题，并防护电子表格公式注入。
- JSON：版本化结构，包含文件基础信息、模式、映射、规则配置、汇总和问题。
- XLSX：ExcelJS 新建独立工作簿，生成“检查汇总”“问题明细”“规则说明”，设置类型、冻结、筛选、列宽和严重程度样式。

所有报告均通过浏览器下载 API 本地保存，不写回输入文件。

## 状态与持久化

工作簿状态属于当前页面会话：

- 原始 `ArrayBuffer`、ExcelJS 对象、行快照和问题列表只在内存中存在。
- 文件名、映射和检查结果不进入 `localStorage`、`sessionStorage`、IndexedDB 或 Cookie。
- `localStorage` 只允许保存主题、语言和通过校验的规则配置。
- “清除文件与结果”重置工作簿相关状态，但可保留用户的非文件偏好。

## 进度与性能

解析和检查分别报告阶段。对工作表和明细的长循环按批次处理，并在批次间把控制权交还浏览器，避免持续阻塞交互。结果表只渲染当前分页（25、50 或 100 条），不会一次挂载全部问题。

性能测试应至少覆盖 10,000 条明细。超大、损坏、加密、空工作簿、无可见工作表、识别失败和无明细分别转换成用户可理解的错误/空状态，不向控制台泄漏未处理异常。

## 构建与部署

### GitHub Pages

标准 Vite 构建使用 `/boq-lint/` base，产物位于 `dist/`。Pages 工作流只部署静态产物，具有 `contents: read`、`pages: write` 和 `id-token: write` 的最小权限。

### 单文件离线版

离线构建使用独立 Vite 配置和 `vite-plugin-singlefile`，将脚本、样式和必要资源内联，并使用适合 `file://` 的资源路径。最终文件为 `release/boq-lint-v0.1.0.html`，配套 SHA-256 文件由打包流程生成。

离线版与 Pages 版使用相同的解析、规则和报告代码。端到端测试直接以 `file://` 打开产物，加载虚构示例并完成检查，同时拦截网络请求。

## 信任边界与威胁

所有导入内容都不可信，包括文件名、工作表名、单元格文本、公式、缓存结果和 JSON 配置。主要控制包括：

- 不使用 `dangerouslySetInnerHTML` 展示工作簿内容；
- 不执行宏、公式、外部链接或嵌入脚本；
- 校验配置结构和数值范围；
- 为 CSV/XLSX 文本导出做公式注入防护；
- 限制文件类型/大小并分批处理；
- 不记录工作簿内容到日志；以及
- 构建不依赖 CDN、外部字体、运行时 API 或遥测。

更多边界见 [privacy.md](privacy.md) 和 [../SECURITY.md](../SECURITY.md)。

## 测试策略

- **Vitest**：表头同义词、手动表头、行分类、数值解析、Decimal 计算、每条规则、模式差异、配置校验和三个报告格式。
- **Testing Library**：关键组件状态、键盘交互、双语文本和可访问性语义。
- **Playwright**：正常/问题示例、映射修改、筛选搜索、三种导出、语言/主题、无上传请求和 `file://` 离线检查。
- **发布验证**：完整 npm 质量门禁、离线 SHA-256 校验、截图尺寸/内容检查和敏感数据扫描。

## 扩展原则

新规则应保持可解释、可测试、低误报，并明确适用范围。涉及价格判断、定额、地区完整编码库、自动修改或合规认证的能力不进入核心规则。任何后端、上传、遥测、AI 或持久化工程数据的提议都属于重大架构和隐私边界变更，不能静默加入。
